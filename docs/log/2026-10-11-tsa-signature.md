# The timestamp's signature is verified, not only its digest

**Decided:** `lastlight verify` now proves the RFC 3161 timestamp is genuine before it believes what it says, and `lastlight seal` makes the same check on the authority's reply before it writes anything (issue #25). The trust is FreeTSA's root CA and TSA certificates, committed as PEM files under `src/lastlight/seal/certs/` with a README (source URLs, fetch date, fingerprints, validity). The public ledger day 2026-10-11 still prints `PASS (strip verified)`, and the same file with one bit of its signature flipped prints `FAIL: untrusted timestamp for 2026-10-11: signature: ...`.

- **Pinned trust, not the certificates a response carries.** The two PEMs were fetched from `https://freetsa.org/files/cacert.pem` and `https://freetsa.org/files/tsa.crt` on 2026-10-11. Their DER fingerprints (`a6379e7c...` for the root, `32e841a9...` for the TSA certificate, in full in the README) are also constants in `lastlight/seal/trust.py`, and `load_freetsa` refuses a file that does not match. They are byte-identical, as DER, to the two certificates FreeTSA embedded in the response recorded in `tests/fixtures/seal/stub-forecast.tsr`, so the pins were confirmed against a copy of the service's own output taken on another occasion; a test pins that. The pair is strict: the signing certificate must be the pinned TSA certificate, not merely any certificate the root issued.
- **No trust from outside.** `Trust(root, tsa)` is a value; `tsa.authenticate`, `tsa.request_timestamp`, `ledger.seal` and `ledger.verify` take a keyword-only `trust=` whose default `None` means `trust.DEFAULT_TRUST`, read when the function is called. No environment variable, path or command-line option reaches it (a test scans the seal package's syntax tree for `environ`, `getenv` and `argv`, and pins the exact option sets of `seal` and `verify`). Tests replace the default through one fixture, `trust_test_tsa` in `tests/conftest.py`, which is never autouse. The two files of real-pin tests, `test_seal_signature_oracles.py` and `test_seal_signature_pins.py`, never request it, and fail if they do.
- **Reasons name the check, in a fixed order.** The library reports a bad chain, a bad validity, a bad key usage and a bad signature as one `Error while verifying certificates` exception, with an OpenSSL debug dump inside it. `authenticate` therefore checks, in this order, before asking the library for the verdict: status (the parser), certificate chain (the signing certificate must be the pinned one), validity of both pinned certificates at the token's own time, the TSA certificate's critical `id-kp-timeStamping` key usage, then the signature. The reason starts with the check's name. What the token covers is compared after that, so a forgery is named for the forgery: a late token signed by an unknown authority says `certificate chain`, not `late seal`, and a re-pointed genuine response says `signature`, not `digest mismatch`. A genuinely signed token for other bytes still says `digest mismatch`, and every existing reason is unchanged.
- **Status 1 is refused in `parse_response`.** FreeTSA returns 0. The library refuses 1 ("granted with modifications"), and `seal` and `verify` now agree with it.
- **Expiry is the library's semantics, pinned by tests.** `rfc3161-client` 1.0.9 verifies the certificates at the token's own `gen_time` and has no option for the current time. A test authority whose TSA certificate ended before today accepts a token issued while it was valid, refuses one issued after (the end instant itself counts as expired, as OpenSSL counts it, which the first draft of the check got wrong by one second and the library's own error exposed), and refuses one issued before it began. No `--verbose` flag was added: the README and `docs/ledger.md` state the pinned validity (root to 2041-03-07, TSA certificate to 2040-02-02).
- **Fixtures are a test authority that really signs (`tests/tsa_factory.py`).** A throwaway root and TSA certificate made with `cryptography` (EC P-256, the TSA certificate with a critical `id-kp-timeStamping` extended key usage), and a small DER encoder for the `TSTInfo`, the CMS `SignedData` with signed attributes (content type, message digest, signing-certificate-v2) and the `TimeStampResp`. `make_tsr`, `recorded_tsr` and `EchoTsa` now sign. `openssl ts -verify` accepts them and refuses one with its imprint edited, so the fixtures are real tokens (a test skips where the command is missing).

**Rejected alternatives:**

- **Trusting the certificates the response carries.** That is self-trust: anyone can mint a root and a TSA certificate and sign a token with them.
- **Responses recorded once from FreeTSA for fixed fixture bytes.** Each would be tied to exact forecast bytes and to a recording date, would break the moment the canonical forecast changes (renderer v1 adds a model name), and refreshing them needs the network. The one genuine recording we have stays as the oracle for the pins, where its fixed bytes are the point.
- **Letting `ledger_factory.seal_date` swap the trust itself,** because it already receives `monkeypatch`. That would be a second place that changes the default; the fixture is the only one, and the nine test files that seal on their own request it with one `pytestmark` line each (the others only use the shared `ledger_dir` fixtures, which request it).
- **Reading the library's error text to decide which check failed.** The text is a debug dump of an OpenSSL error stack and changes with the library. It is used only to tell a signature failure from an OpenSSL chain failure that the earlier checks did not predict; everything else is decided from the certificates.
- **A `--verbose` validity line,** in favour of the README and the guide, which cannot go stale on a flag nobody passes.

**What broke:**

- **Every fake timestamp.** The old `make_tsr` patched a copy of the recorded response in place, which only worked because nothing checked the signature. All the tests that reach a fake authority (about a hundred test functions in those nine files fail without the trust fixture) now run on signed tokens.
- **ECDSA signatures are randomised,** so `reply == helpers.recorded_tsr()` failed on the first run: two calls made different bytes. The factory signs with RFC 6979 deterministic ECDSA, so the same arguments give the same bytes.
- **DER is strict about `SET OF` order.** The first encoder put the TSA certificate before the root and the library's parser refused the response (`InvalidSetOrdering`); the certificates and the signed attributes are now sorted by their encoding.
- **A non-critical or wrong key usage looked like a chain failure.** OpenSSL checks the certificate purpose while building the chain, so its error for a bad key usage reads `unsuitable certificate purpose`, inside the same exception as a real chain failure. The staged checks run the key-usage test first and name it.
- **One existing test pinned the old caveat.** `test_the_guide_keeps_its_signature_chain_caveat_until_verify_checks_the_signature` required the sentence saying the signature is unchecked, and its comment said it must go when the check landed. It now requires the opposite and a list of what the new paragraph says. `test_re_pointing_the_recorded_response_changes_its_imprint_bytes_and_nothing_else` read `recorded_tsr()`, which is now a signed token; it reads `repointed_recorded_response()`, the same in-place patch kept as a forgery to refuse, with its assertions unchanged.
- **A scan for the word `environ` matched the word "environment"** in a docstring that says nothing reads it. The test walks the syntax tree instead.
- **`VerifierBuilder.add_root_certificate` appends to its own list in place,** so a builder must never be shared between calls; `authenticate` builds a fresh one each time.

**Known limits:** there is one pinned pair, not a list, so after a re-pin the seals made under the old TSA certificate verify only against the old pair (the README says how to re-pin and what that costs); the current certificate runs to 2040. No revocation list or OCSP response is consulted, because a token cannot carry one: a revoked certificate's old tokens still verify. A token's time is the authority's own claim, and one authority is still a single point of failure. `cryptography` is imported directly by `seal/trust.py` and `seal/tsa.py` (and by the tests) but is only a transitive dependency through `rfc3161-client`, which hands its API `cryptography` objects; `pyproject.toml` was out of scope, so it was not added.

**Next:** the retry and missed-evening slice (#26) builds on `seal-daily` and does not touch these files; if FreeTSA ever rotates its TSA certificate, the first sign is a failed seal naming the certificate chain.
