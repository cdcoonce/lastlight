# HRRR ingest along the sunlight's path

**Decided:** `lastlight.inputs.hrrr` reads the few HRRR messages the forecast needs by byte range, caches each range, decodes it and samples it along the transect (issue #6). `lastlight hrrr-transect --date D` prints the nine default fields every 25 km out to 400 km along the sunset azimuth. A live run reads about 9 MB of a roughly 140 MB file and takes a few seconds.

- **Decoder: ecCodes, through the `eccodes` bindings and the `eccodeslib` binary wheel.** It installs from wheels with `uv` on macOS (arm64 and x86_64) and ubuntu-latest (x86_64 and aarch64), with no system package. It reads both packings HRRR uses (simple, and complex with spatial differencing), computes the Lambert-conformal latitudes and longitudes itself, and can also write GRIB2, which the fixture builder needs to crop a message. The macOS wheels are tagged for macOS 15 and later.
- **Independent check of the decoder.** A second decoder, gribberish (a Rust reader), was run once over the same real messages and agreed to the last digit with ecCodes at both anchor cells of all six fields compared. It is not a dependency; it is the reason the expected values in the tests are not just "whatever ecCodes says".
- **The idx and the file are checked against each other.** A range must start with `GRIB` and end with `7777`; a decoded message must be the parameter the field names (discipline, category, number, surface type), the cycle date and hour that were asked for, and the forecast hour that was asked for; all fields must share one grid. A stale idx, a mislabelled line or a file served under the wrong URL is an error, not a quiet wrong number.
- **One idx line per field, matched on variable and level.** Total cloud cover appears twice in a file (boundary layer, entire atmosphere); matching on the variable alone would have taken the wrong one, so zero or two matches is an error. A message ends one byte before the next line's offset; the last message of a file has an open end.
- **`latest_run` checks the forecast-hour-18 idx.** The issue says "checking that the `.idx` exists"; hour 0 appears about 50 minutes after the cycle but hour 18, the last file every cycle writes, about an hour and a half after it. Checking hour 18 means a run counted as complete has every earlier hour too. The run must also be at least two hours old, and up to six earlier cycles are tried before giving up.
- **Choosing the run for an evening (`plan_run`).** The target is the whole hour nearest the sun reaching geometric elevation 0 at the reference point. With neither `--cycle` nor `--fhour`, a past evening reads that hour's analysis (forecast hour 0) and a coming one reads the newest complete run at the forecast hour that reaches the target. The instant itself is internal and is never printed.
- **Sampling is nearest cell, and a point more than half a cell diagonal (plus 1 percent) from every cell centre is off the grid.** That raises `OutsideGridError` for the whole call; no half-filled table. Each row records the method, the cell used and how far the cell centre is from the point.
- **A cell the model leaves empty is `None`, never NaN.** Cloud base and top have no value where there is no cloud; the file marks those cells with a bitmap and the code 9999. The decoder swaps that code for a sentinel far outside any physical value before reading, so 9999 cannot pass as a height of 9999 gpm, and masked cells come back masked. Any non-finite value in unmasked data is an error. The CLI prints a dash.
- **Transport is a small protocol.** `UrllibTransport` is the real one; tests pass a fake that serves the recorded files and records every request, so what is asked for (exact ranges, no whole-file read, no repeat request on a cache hit) is tested, not only what comes back. A server that ignores `Range` and answers 200 is refused before a byte of the body is read. There are no retries: a flaky bucket should fail the run, and the seal job (#8) can decide its own retry policy.
- **The cache** is a file per URL plus range (`<sha256>.grib2`), written to a temporary name and renamed, and a cached file that is the wrong length or lacks the markers is dropped and fetched again. The idx is always read again, because it names the ranges. The CLI caches under `data/hrrr`, which git ignores.
- **Fixtures** (`tests/fixtures/hrrr/`, about 380 kB; the issue allows 2 MB): the real idx of one run, verbatim, for byte-range selection against NOAA's offsets, and the nine default fields cropped to 141 by 151 cells around Phoenix, with an idx of their own, so the whole fetch path runs offline. `tools/make_hrrr_fixture.py` rebuilds them from the bucket and fails if a cropped value differs from the original; running it again reproduced the committed files byte for byte.
- **The reference point is repeated in the command module** (33.45, -112.07) because `lastlight.site` is not on every branch yet; it should import it once it is.

**Rejected alternatives:**

- `pygrib`: no wheel for macOS arm64 in any version (checked by resolving it for each platform with `uv`), so it would need system packages on the machine this is built on.
- `cfgrib`: a thin layer over ecCodes that drags in xarray and a dataset model; we want one 2-D array per message and the grid.
- `gribberish`: decoded every message correctly, but it only reads, so the fixture could not be cropped with it, and the grid coordinates would have had to be rebuilt by hand from the Lambert parameters.
- Downloading the whole file once and slicing it: 140 MB per forecast hour for nine messages.
- Interpolating between cells: the issue accepts nearest cell for v0, a 3 km cell is far finer than the structure this model resolves, and the method is recorded in every row so a later slice can change it.
- Merging adjacent byte ranges into one request: fewer requests, but the cache key is URL plus range, so a merged range would defeat the per-message cache. Nine small requests are fast enough.

**What broke:**

- **`uv add eccodes` produced a lock with no native library.** The `eccodes` wheel depends on `eccodeslib` only off Windows, and uv's universal lock took the dependency list from the Windows wheel, so `import eccodes` failed with "Cannot find the ecCodes library" on this Mac right after `uv sync`. `eccodeslib` is now listed explicitly, with a comment saying why. A plain `uv pip install eccodes` had worked, which is why the first trial in a scratch environment did not show it.
- **The first crop was too small.** A 400 km transect toward the equinox sunset azimuth runs 133 cells west, and toward the June azimuth about 190 km north; the first crops (130, then 140 cells west, but only 60 or 70 cells north) lost the end of the transect for part of the year. The all-seasons test caught it. The crop is now 50 cells south, 90 north, 140 west and 10 east of the reference cell.
- **Re-encoding at the original bit depth lost up to 16 m of visibility** (12 bits over the crop's smaller range re-quantises). The crop is written at 24 bits per value and the builder checks every cropped value against the original.
- **`main` moved twice while this was built** (the renderer, then the privacy scanner); the branch was rebased onto the new main before the pull request.
- **A test expected a closed range for the last message of the crop.** The idx gives it no end, so the request correctly has none; the test now says so.

**Known limits:** the nearest cell is a 3 km value, not an average over the sightline; HRRR cloud base and top heights are in geopotential metres and the file does not say whether they are above sea level or ground, which the renderer slice must settle before using them; aerosol optical thickness in HRRR is zero unless the smoke run is active, so a flat zero is not evidence of clean air.
