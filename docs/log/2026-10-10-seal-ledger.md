# Seal ledger

**Decided:** `lastlight seal` and `lastlight verify` make honesty rule 1 executable. A forecast is validated, written as canonical JSON, hashed with SHA-256, witnessed by an RFC 3161 timestamp and indexed; `verify` re-derives the digest and checks that the timestamp was issued before geometric sunset at the reference point (issue #5).

- **Library: `rfc3161-client` 1.0.9, not `asn1crypto`.** Both were allowed. `asn1crypto` is pure Python but has had no release since 2022; `rfc3161-client` (Trail of Bits, used by sigstore) is current and ships the verifier the signature-chain follow-up needs. It is not pure Python: it is a Rust extension in abi3 wheels, pulled in through `cryptography`, and `uv.lock` carries wheels for macOS and Linux. Schema: pydantic 2.14, for strict typing, `extra="forbid"` and a JSON schema for free.
- **The request has no nonce.** The imprint is the forecast's own digest, so a replayed response can only ever cover the same digest, and TLS protects the channel. Without a nonce the request bytes are deterministic, so the test pins them exactly (they are the bytes the public TSA accepted when the fixture was recorded). `certReq` is set so responses carry the TSA certificate for the follow-up.
- **The imprint is the digest.** The TSA is asked to timestamp the canonical bytes with SHA-256, so the response's imprint equals `sha256(canonical_bytes)` and the index digest. `verify` hashes the file as it sits on disk and compares it with the imprint, then also requires the file to be a valid forecast for the requested date in canonical form.
- **The recorded fixture is real; the variants are patched copies.** `tests/fixtures/seal/stub-forecast.tsr` is a response from freetsa.org for the stub forecast's canonical bytes, recorded once through the real client. Scenario tests (late, boundary, other digest) re-date a copy by patching the fixed-width imprint and `GeneralizedTime` bytes in place, computing the time from the geometric sunset so that no test writes a clock time. The copies' signatures no longer match, which is fine until the signature-chain follow-up lands (that slice must stop using patched copies, or sign them).
- **Validation goes beyond the issue in two places.** Every string field is checked with the privacy scanner's text rules (P001, P002, P003), not only P001: the ledger is append-only and `privacy-scan` runs over it, so a leak sealed once could never be removed and would fail CI forever. And `reference_point` must be the public reference point, so the private camera coordinates cannot be sealed by mistake. Neither check echoes the offending text.
- **`cycle_hour_utc` stays.** The issue prescribes it and it is the public weather-model cycle label (the 18 of an 18Z run), not a time of anything lastlight did. Design section 3 says "no UTC"; that line is about times, and this is an integer 0 to 23. Flagging the tension rather than resolving it silently.
- **Seal order and atomicity.** The date is checked first (any of the forecast file, the timestamp file or an index row refuses, before a timestamp is spent), the TSA is asked second, files are written last with exclusive create, the index line last of all. A failure while writing removes what this seal wrote; a lost race is reported as already sealed and removes only this seal's own files.
- **Exit codes.** `seal`: 0 sealed, 1 the TSA or the disk failed (nothing left behind), 2 refused (invalid or unreadable forecast, or already sealed). `verify`: 0 PASS, 1 FAIL (a missing seal is a FAIL, not a usage error), 2 unusable arguments. FAIL reasons give the lateness as a duration and never print a clock time.
- **Canonical floats follow Python's `repr`** after rounding to six significant digits. Negative zero is written as zero. Rounding is relative, so a value that is exactly 0.0 in one run and 1e-17 in another still hashes differently; the renderer slice should snap exact zeros if it can produce them either way.

**Rejected alternatives:** a nonce in the request (no gain, loses determinism); hashing parsed-and-reserialised JSON in `verify` instead of the file bytes (would let a reformatted file pass); `file`/`ftp` TSA URLs (urllib would open them, so the client allows only http and https); a default `--ledger-dir` (a stray `ledger/` in the wrong working directory would seal into the wrong place); an index cross-check in `verify` (the timestamp is the witness, the index is a listing).

**What broke:**

- The first privacy-scan run over the tree flagged 16 lines in my own tests, because a rejection test has to contain the thing it rejects. The leak-shaped strings are now assembled from parts in `tests/seal_helpers.py`, so no test file spells a clock time, a sun-event time or an off-reference coordinate.
- pydantic refuses `strict` on a `Literal`, so `schema_version` is a plain `Literal[1]`; and its JSON parser rejects a lone surrogate before any validator runs, so the UTF-8 check is only reachable from Python input.
- A mutation sweep (about 55 injected defects) left survivors that each became a test: an index without a trailing newline, a `file://localhost/...` URL, an unbounded response read (the second size check hid it), an infinite vividness spread (`ge=0` alone lets it through), the lateness units in the FAIL reason, the exclusive-create race, and compact or ISO-week dates reaching `fromisoformat`. Two survivors were equivalent mutants: the naive-datetime guard (the library always returns UTC, so the dead guard was deleted) and echoing pydantic's input (the CLI never prints it, so the flag changes nothing).

**Not covered:** the TSA's signature chain and certificate validity (follow-up); a TSA that reports `genTime` with fractional seconds beyond what `datetime` holds; clock skew (a timestamp issued a second before sunset passes); verifying that the TSA is the one the repo expects.

**Next:** the signature-chain follow-up, HRRR ingest, then the scheduled workflow that seals at a fixed clock time (it adds its own allowlist entry with a reason).
